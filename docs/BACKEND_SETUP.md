# Backend foundation — setup notes

**Purpose:** Explain the backend foundation and its safety boundary so local setup is reproducible without mistaking the current API shell for a customer-ready service.

## Current state

- `server/migrations/0001_core.sql` defines tenant-scoped PostgreSQL records, row-level security, and append-only stock/financial/audit history.
- `server/migrations/0002_store_profile.sql` adds versioned store contact and receipt-footer fields for server-backed settings.
- `server/migrations/0003_password_recovery.sql` adds expiring, single-use password-reset tokens.
- `server/migrations/0004_export_lookup_indexes.sql` adds store/date indexes used by bounded exports and their date filters.
- `server/migrations/0005_cash_tender_history.sql` stores cash received and change on each order, and backfills historical cash receipt from successful cash payment rows. Earlier change values were not recorded, so those historical rows remain zero for change rather than inventing values.
- `server/migrations/0006_store_invitations.sql` adds hashed, expiring store invitations with pending-account claims and row-level policies for owner and invitee flows.
- `server/migrations/0007_cash_register_sessions.sql` adds one active cash-register session per store, opening float, counted closing cash and variance, and an optional session link on cash movements.
- `server/migrate.js` serializes migration runs with an advisory lock, stores a checksum for each applied file, and refuses to run an edited migration as if it were new.
- `server/db.js` exposes an application pool and transaction helpers that set user/store context and check active store membership before business queries.
- `server/index.js` serves only an allowlist of Slink assets, adds security headers, and exposes liveness/readiness endpoints.
- Production startup and migrations require `PG_SSL=true`; the PostgreSQL client verifies the server certificate instead of silently falling back to plaintext or trusting any certificate.
- API request logs use the matched route template, response status and duration rather than raw URLs; Fastify's `LogController` suppresses automatic request logging for API and query-string URLs so customer searches and token links do not enter application access logs as raw URL values.
- `server/auth.js` provides account registration, email verification, password recovery, sign-in/out, current-session, store-listing, opaque database-backed sessions, and same-origin/CSRF checks. Email delivery does not follow redirects. Development without an email delivery endpoint returns verification and reset links through API responses; production refuses to start unless an HTTPS public origin and authenticated HTTPS email-delivery endpoint are configured.
- `server/staff.js` provides owner-only staff listing, email invitations, invite-based account creation, acceptance after verified email, resend/revoke, role updates, suspension/reactivation and audit events. Development returns the invitation URL; production relies on the configured email provider. The PostgreSQL application role must be granted `SELECT`, `INSERT`, and `UPDATE` on `public.store_invitations` in addition to the existing workflow tables.
- `server/cash-register.js` opens and closes store cash sessions. Cash sales/change, cash refunds, debt collections, supplier payments, purchase payments and manual cashbook movements require an active session and carry its ID. Non-cash tender is excluded from expected drawer cash. A close records counted cash; a nonzero discrepancy requires a reason and creates a cashbook adjustment and audit event in the same transaction. Only one session may be open per store; a cashier may close only their own session. The PostgreSQL application role must be granted `SELECT`, `INSERT`, and `UPDATE` on `public.cash_register_sessions`.
- `GET /api/stores/:storeId/cash-register` returns the active session and the 10 most recently closed sessions. Cashiers receive their own closed sessions; owners, managers, and accountants can view store-wide history. The Finance UI shows the session open/close actors, reconciliation totals, variance and reason. Cashbook rows show the recording actor and session association; the CSV export includes session ID and opening time.
- Finance read routes are role-scoped: owners, managers, and accountants receive financial totals, debtors, payables, cashbook and analytics; cashiers receive current/their-own cash-session ledger rows; stockkeepers receive supplier names and purchase records for receiving but no cashbook, debt totals or analytics. The browser hides financial dashboard metrics and reports for cashier/stockkeeper roles. This boundary has only received static code review so far and still requires per-role API acceptance.
- `server/products.js` provides authenticated, store-scoped catalog listing/search, create, version-checked update, and archive. Catalog mutations are transactional and write audit/cost history.
- Product search/list responses, inventory rows, stock valuation summaries, and order-line detail omit cost values for cashiers. Customer and order history endpoints deny the stockkeeper role; their list queries also filter explicitly by store ID in addition to row-level security. The browser hides POS, orders and customer areas from stockkeepers and POS from accountants.
- `server/sales.js`, `server/returns.js`, `server/payments.js`, `server/stock.js`, `server/purchases.js`, `server/finance.js`, `server/analytics.js`, and `server/records.js` expose transactional retail workflows with store scoping, role checks, idempotency for retried writes, stock/order locks, audit events, and ledger entries. Local PGlite acceptance includes split tender, non-cash overpayment rejection, changed-key payload conflict, unpaid-order void and replay, plus an insufficient-stock rollback/retry. Payment providers are not connected, so payment amounts are operator-recorded confirmations.
- Customer onboarding can create an opening receivable ledger debit; supplier onboarding can create or reuse a supplier and record an opening payable. Both operations use idempotency and audit records, and opening balances do not create cash movements. Only owners, managers, and accountants can record an opening balance.
- The browser client has registration, sign-in, email verification, password reset, session restoration, sign-out, a searchable server-backed catalog and connected POS, order detail/returns, customer records, inventory adjustment, purchase receiving/history/details, supplier payment, cash movements, analytics, version-checked store profile settings, and an owner-only staff invitation/role screen.
- `server/exports.js` provides authenticated store-scoped CSV downloads for catalog/inventory snapshots and movement history, customer/supplier profiles and ledgers, orders and order lines, payments, returns/refunds, cashbook, and purchases. It limits finance/customer exports to owner, manager, and accountant roles, and stock/purchase exports to owner, manager, stockkeeper, and accountant roles. Each successful export is audited. It exports up to 50,000 rows per file, supports inclusive store-time-zone date ranges, preserves VND as integer text, and rejects oversized exports instead of returning partial data. All 14 datasets returned 200 with a UTF-8 BOM on the local PGlite role; native PostgreSQL, authorization/date/row-limit boundaries and phone downloads remain unverified.
- The browser exposes the CSV export dialog from the products, orders, customers, inventory, and finance screens. Export files come from the server rather than the loaded list page; this is a data export workflow, not a database backup or restore procedure.
- Checkout accepts up to five distinct tender methods, records each applied payment, writes actual incoming cash plus a separate change outflow, and persists the cash received/change amounts on the order. Non-cash tender cannot exceed the order total. Single-method pending requests retain their prior idempotency hash so an in-flight sale can still be retried after the client update. Split cash/bank-transfer, same-key replay, changed-payload conflict, and non-cash overpayment rejection passed on local PGlite; native PostgreSQL and device acceptance remain open.
- Owners and managers can void an unpaid, unreturned order with a required reason and explicit confirmation that goods were not delivered or are back in the store. The server locks the order, restores only stock movements recorded by that sale, writes customer-ledger and stock reversal entries, updates the order status, and audits the reason in one transaction. Local PGlite accepted the confirmation requirement, inventory/debt reversal and repeated-void no-op. Orders with any payment must use return/refund handling; native PostgreSQL and device acceptance remain open.
- Product/customer/order list APIs are paginated. The POS and purchase pickers search the full active catalog through the API rather than only searching the first loaded page.
- Product CSV onboarding imports up to 200 products with optional opening stock in one transaction after client preview and server validation; customer opening receivables and supplier opening payables are ledger entries and do not create cash movements. These flows have local PGlite API evidence, but browser file selection, reload recovery and native PostgreSQL acceptance remain open.

## Local development runtime

- `pnpm dev` starts the same Fastify API and PWA with PGlite, using the real migration files and a non-owner `slink_app` role for application transactions. PGlite runs in one process and serializes local requests; it is only a convenient local development runtime. The app-shell service worker uses network-first requests with the cached shell as its offline fallback.
- The database persists in `.local-data/pglite` by default. Set `SLINK_LOCAL_DATA_DIR` to use another local folder. This path is ignored by Git and contains business data; keep it private and back it up before deleting or moving it.
- On this Windows development machine, a native PostgreSQL 18 cluster persists in `.local-data/postgres-native` and listens only on `127.0.0.1:5433`. The one-time setup created distinct random `slink_migrator` and `slink_app` credentials in the ignored, ACL-restricted `.env`; the app role is a non-superuser with `NOBYPASSRLS`, no schema `CREATE` privilege and no read access to `schema_migrations`. The PostgreSQL administrator secret is DPAPI-encrypted under the current Windows account. Use `pnpm db:postgres:start`, `pnpm db:postgres:status`, and `pnpm db:postgres:stop` to manage this cluster; `pnpm start:native` starts the cluster and Fastify together. This is local development infrastructure, not a managed production deployment.
- `server/import-pglite-to-postgres.js` supports an explicit one-time local import from a **copy** of a PGlite data directory. It refuses production mode, a non-local PostgreSQL target, the original `.local-data/pglite` path, a missing account-verification email, or a destination that already contains business rows. It imports compatible columns in a single transaction; migrations stay managed by the native target. Supply `SLINK_IMPORT_TARGET_URL` only for the import process and `SLINK_IMPORT_VERIFY_EMAIL` for the account check; never save a superuser URL in the repository. On 2026-10-15, a temporary snapshot copy imported 25 tables and 146 rows to the empty native database, and the original PGlite directory was preserved.
- Disposable PGlite acceptance has applied all seven production migrations and exercised health/readiness, account registration and verification, sign-in, product create/list, stock adjustment, cash sale/change, split tender, retries, changed-payload conflict, non-cash overpayment rejection, partial return/restock, unpaid-order void, out-of-stock rollback/retry, purchase receipt, supplier partial payment, customer debt collection, finance/analytics reconciliation, all 14 CSV datasets and restart persistence. Account, order, refund and stock survived a server-process restart. Separate disposable PGlite runs accepted staff invitation and suspension, password recovery, product CSV import, customer/supplier opening balances, cash session open/close, cash-flow linkage, expected cash reconciliation and variance handling. Audit-failure injections across sales, returns, purchases, payments, voids, stock counts, manual cash, store settings and cash-session close rolled back the related business writes; safe same-key retries committed once where supported. These are local API slices. They do not establish native PostgreSQL, browser file selection/reload recovery, concurrency across devices, production roles, backup/restore or device acceptance. The existing `.local-data` business database was not used for disposable acceptance.
- This command does not create demo stores or sample transactions. Register through the app; development returns a verification link because there is no mail provider.
- `pnpm start` continues to use native PostgreSQL from `APP_DATABASE_URL`; `pnpm db:migrate` applies migrations with `MIGRATION_DATABASE_URL`. The PGlite runtime refuses `NODE_ENV=production` and is not production or multi-device deployment evidence.
- Native PostgreSQL evidence is currently limited to applying migrations 0001–0007, verifying password authentication and least-privilege role flags, importing the local snapshot transactionally, and loading a server-backed product list in the browser. A sign-in attempt for the imported account was rejected; that account's email is still unverified, so its password was not validated. The app's development verification-link flow still requires an intentional owner action before sign-in.
- For phone testing on a local Wi-Fi network, bind `HOST=0.0.0.0` and set `PUBLIC_ORIGIN` to the computer's LAN origin. Use HTTPS and real devices for install, cookie, accessibility, and platform acceptance; local HTTP testing alone does not pass those gates.

## Connection roles

Use separate PostgreSQL credentials:

- **Migration role:** temporarily runs schema changes; has the necessary DDL rights.
- **Application role:** non-superuser, `NOBYPASSRLS`, does not own the tables, and only has the data privileges needed by the API. It must not be able to create/alter schema or read `schema_migrations`.

The application must use `APP_DATABASE_URL`; migration tooling must use `MIGRATION_DATABASE_URL`. Do not reuse a superuser connection for the running API, because superusers bypass row-level security. The repository does not contain database credentials.

## Local environment

1. Install dependencies with the project package manager.
2. Create a PostgreSQL database and the two roles above; do not use production data during development.
3. Copy `.env.example` to `.env` and replace the placeholder connection strings with local development credentials. Never commit `.env`.
4. For local development, registration returns a verification link because no mail provider is required. For production, configure `PUBLIC_ORIGIN` to the HTTPS site origin, `EMAIL_DELIVERY_URL` to an HTTPS endpoint that accepts JSON `{ "to", "subject", "text" }`, and `EMAIL_DELIVERY_TOKEN` as its Bearer credential. The delivery endpoint must return a 2xx response only after accepting the message. Do not expose the development verification-link behavior in production.
5. Run the migration command, then start the server. `GET /api/health` reports process liveness; `GET /api/ready` reports database connectivity.
6. The current API checks use PGlite with a non-owner `slink_app` role. PGlite validates migration SQL and basic tenant/constraint behavior; it is not a replacement for running the same migrations, role grants, and workflows against the selected native managed PostgreSQL service.

## Deployment boundary

Production still needs an approved HTTPS domain, managed PostgreSQL, secret injection, backups/restore, monitoring, and a provider role setup. Set `PG_SSL=true` in every production environment; the PostgreSQL client verifies the certificate and rejects untrusted certificates. Configure the selected database service's CA trust through the supported Node.js certificate configuration if it uses a private CA. Set `TRUSTED_PROXY_IPS` only to the actual proxy address/CIDR; do not trust arbitrary forwarded headers.

Do not expose this version to real customer data or describe it as ready to sell. Browser workflow verification beyond the tested screens, iOS/Android device verification, durable offline synchronization, domain acceptance verification, native PostgreSQL role and workflow evidence, backups/restore, privacy documents, monitoring, and release operations remain open in `DELIVERY_ROADMAP.md`. Production email delivery and the staff flow on native PostgreSQL still need provider and database acceptance.
